## Summary

Reviewed at HEAD `6e225905` (player/audio tree identical to the audited baseline `eca648a8`; only docs commits on top). Scope: `NuvioMpvSurfaceView`, `PlayerMediaSourceFactory`, track enumeration/selection, delay, seek, lifecycle, failover, headers, external-player launch, and the exact local Media3/mpv binaries.

Falsification result, split by claim:

- **Falsified: "MPV finalized-artifact pilot is a small wrapper change."** Statically, the pilot is viable — the exact binary shipped in `app-full-arm64-v8a-debug.apk` is byte-identical to `mpv-android-lib:0.1.12`'s `libmpv.so` (SHA-256 `ea485887c3663a69c7ea9586530e173fda8d498f67891e29909ddcf06bf19f16`, self-reported `v0.41.0-174-g76a5eba99`), the `audio-add`/`audio-remove`/`audio-reload` command strings are present in that `.so`, and the wrapper's JNI (`MPV_commandNode`, `MPV_observeProperty`) is sufficient for a tested adapter. But the wrapper work is the small half: attachment is not durable across at least seven distinct rebuild/loadfile paths (Finding 2), failover restore matches audio by language/name and would silently reselect the wrong embedded track (Finding 3), and no code path distinguishes auxiliary failure from primary failure, so a dub 404/decoder error consumes whole-player retry and engine-failover budget (Finding 4). The pilot is an identity/lifecycle/error-classification change wearing a wrapper-change costume.
- **Falsified: the DASH half of the localhost HLS/DASH target.** The bundled mpv contains no DASH demuxer (no `dashdemux`/MPD demux strings in `libmpv.so`; upstream mpv/FFmpeg ship none). Lane 05's "MPV understands HLS/DASH broadly" is wrong for DASH: an MPD handed to mpv fails to load. The cross-engine contract must be HLS-first (or a remuxed progressive/segmented format); DASH can only ever be a Media3-side option (Finding 5).
- **Falsified: "both engines just open one URL" under current error handling.** `PlayerLoadErrorHandlingPolicy` returns `TIME_UNSET` (no retry) for any 400/401/403/404/410. One 404 on an advertised-but-evicted loopback segment hard-fails the primary load and drops the player into the full rebuild ladder (Finding 4). The proxy needs an explicit never-404-an-advertised-segment invariant plus a loopback-aware error class.
- **Falsified: reusing existing networking for anything provider- or artifact-adjacent.** The playback stack inherits a trust-all TLS fallback, deliberately re-adds `Authorization` on cross-host redirects, and shares `NuvioApplication.extensionCookieJar`; MPV serializes primary credentials into the **global** `http-header-fields` property that governs every HTTP fetch mpv makes — including external tracks added later (Finding 7). A live variant of this leak exists today for external subtitles.
- **Confirmed:** single-source construction with a single delay wrapper (Finding 6), the ±3000 ms/25 ms persisted route delay with no base/correction split (Finding 8), teardown and external-handoff ordering that would strand a dub session or loopback server (Finding 9), and a diagnostics void on the MPV side (Finding 10).

Binary identity receipts (this review, host machine): `mpv-android-lib-0.1.12.aar` SHA-256 `bb1a007c545cc7ac3304293ae79866b5361a48449ee7648c4030d5355869effc`; APK `lib/arm64-v8a/libmpv.so` SHA-256 `ea4858…f19f16` identical to the AAR's; forked local AARs' `MediaLibraryInfo` constant pool self-identifies as `1.8.0` (`AndroidXMedia3/1.8.0`) — so all merge/HLS behavior must be tested against 1.8.0-era binaries, not current documentation. Static string presence is necessary-but-not-sufficient: every command/seek/DASH claim still requires the on-device probes below before code merges.

All findings below are pre-existing seams the pilot must not inherit blindly; none endangers current users today. Priorities are pilot-blocking severity, not current-bug severity.

Finding: MPV external-audio adapter does not exist; header plumbing is global and CRLF-unsafe
Evidence: `NuvioMpvSurfaceView.kt:455-481` implements only `sub-add` (`addAndSelectExternalSubtitle`); there is no `audio-add`/`audio-remove`/`audio-reload` anywhere in the tree (repo-wide grep finds no dub/external-audio code outside YouTube-trailer naming). `applyHeaders` (`NuvioMpvSurfaceView.kt:624-638`) serializes headers into the single global `http-header-fields` property, escaping only `\` and `,`. Static binary inspection of the exact shipped `libmpv.so` (SHA-256 `ea4858…f19f16`) finds the `audio-add`, `audio-remove`, `audio-reload` command-name strings and the `MPV_commandNode`/`MPV_observeProperty` JNI symbols in `libplayer.so`, so the adapter is buildable against `mpv-android-lib:0.1.12` (mpv `v0.41.0-174-g76a5eba99`).
Impact: The Phase A pilot cannot start without this adapter, and any naive implementation that attaches a remote URL while primary credentials sit in the global header property sends debrid `Authorization`/`Cookie` to the artifact host (or fails if headers conflict). Values containing embedded CR/LF survive `sanitizeHeaders` (which only trims ends and drops `Range`, `PlayerMediaSourceFactory.kt:322-354`) and reach mpv's HTTP layer — header injection against whatever host mpv fetches.
Fix: Add `NuvioMpvSurfaceView.addExternalAudio(url, title, lang, flags)` / `removeExternalAudio(id)` / `reloadExternalAudio(id)` issuing `mpv.command("audio-add", url, "select", title, lang)` etc., with per-file options (never global header mutation) and result booleans surfaced for tests. Attach only credential-free `127.0.0.1` tokenized URLs. Reject CR/LF and control characters in every header value at the shared sanitization seam before mpv or OkHttp see them.
Priority: P1
Confidence: high

Finding: External-audio attachment is not durable — every rebuild/loadfile path silently drops it
Evidence: mpv external tracks are per-file, and `NuvioMpvSurfaceView.setMedia`/`setMediaUsingLoadfile` end in `loadfile ... replace` (`NuvioMpvSurfaceView.kt:59-125`) with `applyDefaultTrackSelectionForNewLoad()` resetting `aid`/`sid` to auto (`:134-144`). Rebuild/loadfile call sites that would discard an attached dub with no reattach: startup engine failover (`PlayerRuntimeControllerEngineFailover.kt:43-62`), manual engine switch (`:66-132`), stream switch (`PlayerRuntimeControllerStreams.kt:787-874`), episode/source switch (`:1324-1465`), auto-retry first/second attempts (`PlayerRuntimeControllerErrorRecovery.kt:283-296`), startup recovery (`:61-62`), PCM audio fallback and DV7/VC-1 rebuilds (`:377-381`, `:426-430`, `:477-489`). Contrast: subtitles have dedicated reattach machinery (`effectiveSubtitleSelectionForEngineSwitch`, `pendingRestoredAddonSubtitle`, `refreshSubtitlesForCurrentEpisode` in `PlayerRuntimeControllerObservers.kt:154-202`); audio has none.
Impact: A user playing with the translated-voice overlay loses the dub on the first retry, engine switch, or episode autoplay, with no state, toast, or reattach — directly violating the acceptance gates "source/episode switch removes the old generation before loading the next source" and "failover recreates or explicitly drops the dub with a truthful UI state". 100-cycle attach/remove tests will pass in isolation and still ship a dub that vanishes in production.
Fix: Introduce a `DubPlaybackCoordinator`-owned descriptor in controller state (not `TrackInfo`/view state) with a monotonically increasing generation, and one idempotent `attachCurrentDubGeneration()` invoked from every path that calls `initializePlayer`/`initializeMpvPlayer`/`setMedia` — the exact enumeration above is the integration checklist. Cancel/expire the generation before `currentStreamUrl`/`currentHeaders` are overwritten in `PlayerRuntimeControllerStreams.kt:578-579` and `:1360-1361` so a late artifact from episode A cannot attach to episode B.
Priority: P1
Confidence: high

Finding: Engine-failover capture discards dub origin and restores audio by language/name only
Evidence: `captureCurrentAudioSelectionForEngineSwitch` (`PlayerRuntimeControllerEngineFailover.kt:196-247`) reduces MPV audio to `RememberedTrackSelection(language, name, trackId)`. `MpvTrack.isExternal` exists (`NuvioMpvSurfaceView.kt:712-725`) and `applyMpvTrackSnapshot` does map external audio into the rail (`PlayerRuntimeControllerMpv.kt:305-330`), but `TrackInfo` carries no origin/external flag (`PlayerUiState.kt:239-250`) and `rememberAudioSelection` persists dub choices by language/name (`PlayerRuntimeControllerTrackSelection.kt:83-107`), feeding `applyPersistedTrackPreference` on later episodes. Additionally, any mid-session `applyAudioLanguagePreferences` call re-runs `aid=auto` selection by `alang` (`NuvioMpvSurfaceView.kt:196-212`; settings observer at `PlayerRuntimeControllerObservers.kt:388-397`), silently deselecting a manually selected external track that does not match the preferred language.
Impact: MPV→Exo failover with a "Translated voice (Italian)" track selected restores the *embedded* Italian track (original audio) while the UI believes the dub continues — an untruthful silent fallback. Exo→MPV cannot restore a dub at all (nothing to re-add). Persisted language/name preference can auto-select a same-language embedded track on the next episode, defeating "never match a new embedded track merely by same language/name".
Fix: Add `origin` (`EMBEDDED`/`MANIFEST_RENDITION`/`DUB_EXTERNAL`) and a stable `selectionKey` to `TrackInfo`; keep the `ExternalAudioDescriptor` plus desired selection in controller session state; on failover either reattach by stable key at saved position (proxy/provided the URL is engine-neutral) or explicitly drop with a visible "Original audio" state. Exclude dub-origin tracks from language-based persisted preference matching.
Priority: P1
Confidence: high

Finding: No auxiliary-vs-primary error classification; a dub fault consumes primary retry and failover budget, and loopback 404s hard-fail
Evidence: `isRetryablePlaybackError` (`PlayerRuntimeControllerErrorRecovery.kt:68-115`) treats IO/parsing/decoder errors as whole-player retryable, and `attemptAutoRetry` (`:239-296`) rebuilds the entire player up to twice; audio failures ladder PCM → safe-audio → disabled-audio (`:344+`). Nothing keys on which child/origin failed. `PlayerLoadErrorHandlingPolicy` (`PlayerMediaSourceFactory.kt:735-748`) returns `TIME_UNSET` for 400/401/403/404/410 — combined with `isRetryablePlaybackError`'s same-code exclusion, one 404 on an advertised-but-evicted loopback segment ends that load and escalates to the full rebuild ladder. The MPV engine has no error classification at all (progress polling only, `PlayerRuntimeControllerPlaybackEvents.kt:178-261`).
Impact: A translated-audio 404/expired token/short-file/decoder failure stalls or kills primary video — the exact inverse of "auxiliary failure never fails primary video" — and each such fault burns the two auto-retries and engine-failover chances reserved for genuine primary failures. For the localhost HLS/DASH target this also means the segment ring must be perfect: any 404/410 race between playlist publication, eviction, and a backward seek is a guaranteed hard failure, not a retry.
Fix: Add an error classifier keyed on request origin (loopback token vs primary URL): auxiliary-origin load/decoder errors select embedded audio, keep video, mark the dub state `Original fallback`, and never increment `errorRetryCount`/`startupRetryCount` nor trigger `maybeAutoSwitchInternalPlayerOnStartupError`. Give the proxy a written invariant — an advertised segment is never 404/410 within a back window at least as large as the player's back-seek range, atomic publication only — and encode it as a proxy unit test plus an instrumented backward-seek probe.
Priority: P1
Confidence: high

Finding: The DASH half of the localhost target is not cross-engine — bundled mpv has no DASH demuxer
Evidence: Static strings scan of the exact shipped `libmpv.so` (`v0.41.0-174-g76a5eba99`) finds HLS markers (`hls,applehttp` handling, `hls-bitrate`) but no DASH/MPD demuxer registration; upstream mpv and FFmpeg's libavformat ship no DASH demuxer (only a muxer). Lane 05's architecture table claims "MPV understands HLS/DASH broadly" — the DASH half is false for this binary and for mpv generally. Nuvio's own DASH support is a Media3-only path (`DashMediaSource.Factory`, `PlayerMediaSourceFactory.kt:191-194`).
Impact: A `DubSessionProxy` that publishes "HLS or DASH" is fine only if every cross-engine consumer is HLS; handing `http://127.0.0.1:<port>/manifest.mpd` to MPV fails at load, which under Finding 4's policy can cascade into a primary rebuild if the proxy is the primary URL. Designing to "HLS/DASH parity" wastes a lane on an MPD variant no MPV user can play.
Fix: Freeze the cross-engine contract as tokenized loopback HLS (fMP4/CMAF video + AAC alternate-audio renditions on one media-time grid) or a remuxed progressive fallback; keep DASH strictly as a Media3-side experiment behind its own gate. Record the MPD-rejection receipt (probe P4) in decision docs so the lane claim is corrected rather than re-derived.

Finding: Playback networking is credential-promiscuous — trust-all TLS fallback, forced cross-host Authorization, shared extension cookie jar, and mpv global headers leak into external fetches today
Evidence: `PlayerPlaybackNetworking.kt:24-64` defines a trust-all `X509TrustManager`/hostname-verifier client used as an `SSLException` fallback inside `playbackHttpClient`; `:91-132` adds a network interceptor that re-attaches `Authorization` on every cross-host redirect ("same behavior as mpv/curl"). `PlayerMediaSourceFactory.playbackHttpClient` (`:60-66`) layers `NuvioApplication.extensionCookieJar` onto this client. `NuvioMpvSurfaceView.applyHeaders` writes primary credentials into the global `http-header-fields` that mpv applies to **all** HTTP fetches — so the existing `addAndSelectExternalSubtitle` (`:455-481`) already sends the primary stream's `Authorization`/`Cookie` to third-party subtitle hosts whenever an addon subtitle is attached during authenticated playback.
Impact: Any provider client, artifact fetch, or loopback design that "reuses the existing playback client" violates the security invariants (dedicated client, platform TLS, no inherited trust-all, no primary-header forwarding) and can disclose debrid credentials to unrelated hosts; the subtitle path is a live instance of the same leak the dub path would multiply. The mpv global-header design also makes per-track credentials structurally impossible without per-file options.
Fix: Provider networking gets a dedicated client with platform TLS validation and its own cookie store — never `playbackHttpClient`, never `extensionCookieJar`. MPV receives only credential-free tokenized loopback URLs. Fix the existing leak by clearing/scoping `http-header-fields` around external-track fetches or switching subtitle/track attachment to per-file options. Extend `PlaybackNetworkingSslVerificationTest` with a cross-host Authorization-leak assertion and an mpv-headers assertion.

Confidence: high

Finding: Delay is one clamped, per-route persisted scalar with no base-offset or runtime-correction term
Evidence: `applyAudioDelay` (`PlayerRuntimeControllerPlaybackEvents.kt:35-52`) clamps to ±3000 ms in 25 ms steps (`:31-33`), writes one `audioDelayUs`, pushes one value to mpv (`setAudioDelayMs`), and persists it per output route (`PlayerRuntimeControllerAudioDelayRoutes.kt:63-86`); `applyMpvBluetoothAudioRouteInPlace` re-pins that single value after `ao-reload` (`:239-248`); seeks re-apply the same scalar (`PlayerRuntimeControllerMpv.kt:521-533`, `:466-478`). The Media3 implementation shifts **video** sample timestamps against the requested delay (`AudioDelayMediaSource.kt:70-103`, read-time provider at `:145-170`), so any automated correction loop that nudges this value every tick would keep moving the master presentation timeline.
Impact: The pilot needs `routeDelayMs + dubBaseOffsetMs + runtimeCorrectionMs` as separate terms (display effective, persist only route/user); with one scalar, a dub base offset silently becomes the persisted route delay and is re-applied to non-dub playback on that device, and drift correction has nowhere to live without polluting user calibration or stuttering video timestamps.
Fix: Split the delay composition at one seam per engine (`applyAudioDelay` for mpv, the `audioDelayUsProvider` aggregation for Exo), keep the existing UI as the user/route control, clamp the composite, and reserve automated correction for the proxy/audio side with bounded thresholds per the decision doc — never per-tick writes to the Exo video-timestamp path.
Priority: P2
Confidence: high

Finding: Teardown and external-handoff ordering strand dub sessions; nothing owns the loopback server's lifetime
Evidence: `onCleared` runs `releasePlayer()` then `stopTorrentStream()` (`PlayerRuntimeController.kt:652-667`), and `releasePlayer` tears down engines, jobs, and sinks (`PlayerRuntimeControllerLifecycle.kt:9-75`) with no auxiliary-session revoke step; the dub producer reading the primary (or TorrServer localhost URL) must stop **before** `torrentService.stopStream()` (`PlayerRuntimeControllerTorrent.kt:43-56`) to avoid reads after upstream shutdown. `launchInExternalPlayer` calls `controller.stopAndRelease()` immediately before the intent (`PlayerViewModel.kt:282-367`), and `ExternalPlayerLauncher` (`:25-94`) forwards one `video/*` URI, header extras, resume position, and subtitles only — no audio-track concept; an external player reaching `127.0.0.1` depends on Nuvio's process surviving in the background.
Impact: Without an ordered revoke (generation cancelled → producer stopped → external track detached → player released → artifacts deleted → torrent stopped), late provider output can attach to a dead player or a different episode; killing the app while an external player streams from the loopback URL stalls that player with no explanation; and the dub silently disappearing on external handoff contradicts "explicit consent" UX.
Fix: Make the session/proxy process-scoped and independent of Compose/ViewModel lifetimes, with a bounded, non-main-thread shutdown. Teardown order fixed as above, generation tokens in every callback. External handoff policy: either export one finalized mux/adaptive artifact and launch that, or launch the original after explicit consent — never assume loopback reachability or process lifetime.

Fix: Observe `track-list/count`, `aid`, `audio-delay`, and an mpv log/event hook through the existing JNI observer rather than polling; route dub-session metrics (generation, coverage, delay terms, phase error, fallback reason, segment status) through the session coordinator so both engines share one diagnostics contract. Never log token/header values or transcripts.

## Proposed ownership split

Disjoint lanes for parallel Hammersmith worktrees; each spec states owned files, forbidden files, and its own executable check. Rationale: the two high-risk surfaces (mpv wrapper + loopback server) and (identity/state machine + UI) share no files, and the controller/factory seams — which everything touches — get a single integration owner so lanes never merge conflicting edits.

- **Lane M — MPV external-audio adapter + loopback artifact server.** Owns: `app/src/main/java/com/nuvio/tv/ui/screens/player/NuvioMpvSurfaceView.kt` (additive methods only); new `app/src/main/java/com/nuvio/tv/core/player/LocalMediaArtifactServer.kt`; new `app/src/main/java/com/nuvio/tv/core/player/MpvExternalAudioAdapter.kt` (thin, test-targeted); new JVM tests (header sanitizer, token binding, 127.0.0.1-only bind) and the P2/P3/P5/P7 instrumented probes. Forbidden: all `PlayerRuntimeController*.kt`, `PlayerMediaSourceFactory.kt`, `PlayerPlaybackNetworking.kt`, UI state files.
- **Lane D — descriptor, selection state, overlay UX.** Owns: new `app/src/main/java/com/nuvio/tv/ui/screens/player/ExternalAudioDescriptor.kt`; new `app/src/main/java/com/nuvio/tv/ui/screens/player/DubPlaybackCoordinator.kt` (pure generation/fallback state machine, no Android deps); `app/src/main/java/com/nuvio/tv/ui/screens/player/PlayerUiState.kt` (`TrackInfo` origin/selectionKey, dub UI state); `app/src/main/java/com/nuvio/tv/ui/screens/player/AudioSelectionOverlay.kt` (stable-key row, status/coverage/effective-delay display, one-line Start/Original/Stop/Retry); unit tests for the state machine (seek epoch, late-callback rejection, fallback transitions). Forbidden: `NuvioMpvSurfaceView.kt`, controller files, factory/networking files.
- **Lane I — integration owner (controller + factory seams).** Sole owner of `PlayerRuntimeController*.kt` and `PlayerMediaSourceFactory.kt`: hooks at `initializeMpvPlayer`/`initializePlayer`, `seekPlaybackTo`, `applyAudioDelay` (delay composition), failover capture/restore, the error ladder (auxiliary classifier), `onCleared` teardown ordering, and later `createPlaybackMediaSource(primary, auxiliaryAudio?)`. Applies reviewed patches from Lanes M/D after adversarial review; reproduces every P0/P1 finding. Check: focused build + full `assembleFullDebug` + engine-switch/retry integration tests (P11/P12).
- **Lane T — localhost HLS transport prototype.** New-only: `app/src/main/java/com/nuvio/tv/core/player/dub/DubSessionProxy.kt` + HLS fixture generator + segment-ring unit tests (atomic publish, never-404-advertised invariant, bounded time/byte ring, discontinuity policy) + P4/P9/P10 fixtures. HLS-only for cross-engine; no DASH deliverable. Forbidden: every existing player file.
- **Lane P — binary probe receipts.** New `androidTest` classes only (P0–P14 harness where not owned by M/T); no production source. Emits a JSON receipt (mpv version, command results, timings, memory/FD deltas) committed under `docs/ai-media-research/benchmarks/` or `graphify-out/` per the brief's evidence conventions.
- **Shared rule:** new/modified files ≤400 lines (current largest touched file, `PlayerRuntimeControllerInitialization.kt`, is 2716 lines — Lane I must split by responsibility when editing it rather than grow it); no lane edits `app/build.gradle.kts` (the integration owner bundles any dependency/flag change, e.g. the provider feature policy from the flavor finding); every lane's check runs real behavior and prints precise failure causes — a report-file existence check is invalid.
