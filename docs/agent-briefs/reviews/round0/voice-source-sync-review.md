## Summary

**The premise under attack — "tap the selected audio renderer for original audio while generated audio plays" — does not hold on current NuvioTV code, on either engine.** On ExoPlayer, all audio renderers (MediaCodec, `PlaybackSpeedAwareAudioRenderer`, `FfmpegAudioRenderer`) render into one shared `PlaybackSpeedAwareAudioSink`, and the only PCM interception point is the single-element `AudioProcessor` chain containing `GainAudioProcessor`. That chain (a) sees only the *selected* track, so the moment a translated track is selected the original audio stops flowing through it; (b) has no PCM representation at all while AC-3/DTS/TrueHD passthrough or audio offload is active (`GainAudioProcessor.onConfigure` returns `NOT_SET`, i.e. inactive, for any non-PCM encoding); and (c) has no per-buffer PTS, because Media3's `AudioProcessor.queueInput(ByteBuffer)` contract carries bytes, not timestamps — timing lives inside `DefaultAudioSink`/`AudioTrack`. On MPV, `NuvioMpvSurfaceView` exposes no decoded-audio observation of any kind (`observeProperties()` is empty; the only observation is track-list property polling, and the only external-track command is `sub-add`). A single currently-selected audio renderer therefore cannot feed original audio to a provider while generated audio is selected, without PTS, and across passthrough sessions. Decision doc §"Why this split is required" already concedes this ("a raw `AudioProcessor` callback has no authoritative PTS and may stop seeing original audio once a generated track is selected", `decision.md`); the code inspection confirms it in detail.

**The consequence is a hard prerequisite:** Phase B needs an acquisition path that is independent of the playback render path. This report compares the two viable designs on current code — (A) a host-owned second demux/decoder fed from the same URL/headers Nuvio already resolves, and (B) a host-owned loopback proxy/remux (fFMPEG-style demux → segment → serve tokenized localhost HLS with source-time anchors) through which the *player itself* plays. The comparison (§"Source-acquisition options compared") concludes: independent decoder is the right Milestone 5 *prototype* because it changes nothing about playback and reuses `sanitizeHeaders`/redirect/auth handling unchanged; the loopback proxy is the right *target* transport because it is the only design that gives Exo and MPV one source-time grid, one seek story, and a path back from "generated audio selected" to original audio. The repo already has both precedents to build on and one live warning each: `ParallelRangeDataSource` proves range-parallel host-owned HTTP reads against the primary origin, and TorrServer proves a loopback HTTP media server — but TorrServer's fixed port `8091` collides with `StreamBadgeConfigServer`'s default NanoHTTPD port `8091`, and every existing NanoHTTPD server binds wildcard with no token, so the proxy must not inherit either habit.

**Measured evidence supports none of the sync story yet.** The only direct-S2ST receipt (`2026-08-29-qwen-live-translate.json`) shows 1.52–1.57× output expansion, first audio 1.3–3.5 s after session configuration, no source-timestamp mapping, no invoice record, and (per `model-research-audit.md` §3) no retained raw events or code — it is a self-reported smoke summary. This report therefore defines seven requirement sets (source-time mapping, buffering, segmentation, correction, seek generation, reconnect/failover, long-form measurement) as falsifiable specifications, ten findings (F1–F10), and an experiment matrix (M0–M11) whose cells carry fixtures, commands, metrics and pass/fail gates. Priorities: five P1 (each individually blocking for Phase B), five P2. Confidence is high wherever the claim rests on read code, medium where it rests on the docs' own evidence limits.

## Why one selected-renderer tap cannot feed original audio while generated audio plays

Three independent mechanisms each suffice to break the premise; together they close it.

**1. Selection exclusivity.** ExoPlayer renders exactly one audio track group at a time into one sink. `buildAudioSink` (`PlayerRuntimeControllerInitialization.kt:2065-2096`) is called once per player instance and the resulting `PlaybackSpeedAwareAudioSink` is handed to *every* audio renderer built by `buildAudioRenderers` (`:2098-2136`), including the FFmpeg extension renderer registered at `:2135`. Audio track selection is exclusive by construction (`TrackSelectionOverride` on a single group, `PlayerRuntimeControllerTrackSelection.kt:69-73`). If the translated track is a normal Exo track and is selected, the original track's samples no longer reach the sink; if the original track stays selected, the translated audio never reaches the output at all. MPV has the same shape even more explicitly: one `aid` (`NuvioMpvSurfaceView.kt:420-429`) with no audio mixing of two external tracks in this wrapper.

**2. Passthrough/offload sessions have no PCM to tap.** `PlaybackSpeedAwareAudioSink.getFormatSupport`/`getFormatOffloadSupport` (`PlaybackSpeedAwareAudioSink.kt:99-111`) deliberately *allow* AC-3/E-AC-3/TrueHD/DTS-class passthrough whenever neither Bluetooth nor non-1× speed forces PCM (`:117-127`). In that configuration the sink receives encoded frames, not PCM. The only existing tap point deactivates itself: `GainAudioProcessor.onConfigure` returns `AudioProcessor.AudioFormat.NOT_SET` for any encoding other than `ENCODING_PCM_16BIT`/`ENCODING_PCM_FLOAT` (`GainAudioProcessor.kt:33-38`), so the processor chain is bypassed entirely. A dub session that silently depends on "the sink always decodes" would lose original audio exactly on the AV receivers where users watch films.

**3. No authoritative PTS at the tap.** `AudioProcessor.queueInput(ByteBuffer)` carries bytes only; `BaseAudioProcessor` exposes no presentation timestamps, discontinuity markers, or sink playback-head relationship. `GainAudioProcessor` proves the point: it is a pure sample-value transform (`GainAudioProcessor.kt:40-56`) with no notion of media time. The decision doc's own acceptance gate "first-playable lag measured from source media time, not socket receipt" (brief, Near-real-time sync §2) is unsatisfiable from this seam without a parallel timing authority, which is exactly what an independent acquisition path brings.

Additionally, the one place Nuvio *does* create a second rendering path — `EXTENSION_RENDERER_MODE_PREFER` FFmpeg audio (`PlayerRuntimeControllerInitialization.kt:784-801`) — is not an independent acquisition: the FFmpeg renderer is an alternative decoder for the same selected track in the same player, sharing the same sink and the same exclusive selection. It does not give the provider anything.

## Source-acquisition options compared (clear VOD only)

Both options assume the Phase-A boundary already decided in the brief: providers never receive stream URLs, cookies, Authorization, debrid URLs or file descriptors; the host owns acquisition.

**Option A — host-owned second demux/decoder (read-side parallelism).** The dub session opens its own `DataSource` over the already-resolved `currentStreamUrl` + `currentHeaders`, demuxes (FFmpeg in `ffmpeg-decoder-downmix` is already vendored and GPL-compatible), decodes only the audio track, and emits PCM windows tagged with container PTS.
- *Fits current code:* the header/redirect/auth machinery is proven and reusable verbatim — `sanitizeHeaders` (`PlayerMediaSourceFactory.kt:318-331`), the Authorization-preserving network interceptor for cross-host redirects (`PlayerPlaybackNetworking.kt:94-121`), `normalizePlaybackRequest` userinfo extraction (`PlayerRuntimeControllerStreams.kt:575-585`), and range-parallel reads (`ParallelRangeDataSource`, engaged at `PlayerMediaSourceFactory.kt:115-151`). Playback is untouched; original audio keeps playing on the primary path by construction.
- *Costs:* two origin connections (doubling range loads on hosts that limit concurrency), CPU for a full decode of audio the user never hears, per-container codec coverage, and a mapping layer that must reconcile *its* container timeline with the playback timeline the player reports (`player.currentPosition` is smoothed playback position; MPV reports `time-pos/full`, a playback time that stalls under `paused-for-cache` — `NuvioMpvSurfaceView.kt:160-186`). It is a provider-feed, not a player transport: generated audio still needs somewhere to be rendered.

**Option B — host-owned loopback proxy/remux (player-side convergence).** The session proxy reads the clear source with host-owned credentials and serves a tokenized `127.0.0.1` adaptive presentation (local HLS with video passthrough/remux + generated audio renditions on one source-time grid). The player plays the proxy; original audio remains a rendition; selection (Exo `TrackSelectionOverride`, MPV `audio-add`/`aid`) switches renditions on one timeline.
- *Fits current code:* TorrServer already makes the player consume `http://127.0.0.1:8091/stream?...&play` (`TorrServerApi.kt:145-148`), so loopback-HTTP-as-media-source is an established pattern in this app; Exo handles local HLS via `HlsMediaSource` (`PlayerMediaSourceFactory.kt:197-201`) and MPV plays HLS natively. The brief's Phase-B target transport is exactly this.
- *Costs and hazards, all visible in current code:* (i) MPV request headers are a **global runtime property** (`http-header-fields`, `NuvioMpvSurfaceView.kt:624-639`) — an `audio-add`ed loopback rendition inherits the primary origin's headers (Authorization, cookies) unless cleared per-file; the existing `sub-add` path never has to face this, and the leak would put debrid tokens on a loopback request where any co-resident app can attempt to read them. (ii) The app's server precedent is wildcard-bound, untokenized NanoHTTPD (`AddonConfigServer.kt:20-21` port 8080; `RepositoryConfigServer.kt:16-17` and `DebridFormatterConfigServer.kt:17-18` port 8090; `StreamBadgeConfigServer.kt:27-28` port 8091) — directly against the decision's loopback-only, tokenized, no-header-inheritance invariant. (iii) Fixed-port collision is not hypothetical: `TorrServerBinary.PORT = 8091` (`TorrServerBinary.kt:28,40`) and `StreamBadgeConfigServer` default 8091 share a number. (iv) The proxy must not become an ambient LAN service (the config servers are exactly what the decision says phone key entry must not use).

**Sequencing conclusion (matches the brief's Milestone 5):** prototype A first as the acquisition *proof* (no playback risk, immediate provider feed, reuses networking), prototype B as the acquisition *and* transport *target* (single source-time grid, engine-portable, renditions instead of exclusive selection). Reject any variant of either that exposes primary headers to an auxiliary origin (A's provider client and B's player-facing port both count), blocks the playback audio thread, cannot regenerate an arbitrary seek window, lacks per-chunk source PTS, or would transcribe its own generated output (A fed from the sink would do exactly this — another reason the tap premise must die).

## Requirements (falsifiable)

**R1 — Source-time mapping.** Define `S_t` = normalized source media time in the container's own timeline domain (MKV/MP4 track time base, HLS media sequence + segment PTS, DASH period+PTS), and `P_t` = player position at consumption (Exo `player.currentPosition`; MPV `time-pos/full`, treated as invalid while `paused-for-cache`/`core-idle` is true). Every provider chunk carries `{S_t, generation, seekEpoch, durationMs, sampleRate, channels}`. The mapping must be re-anchored at: playback start, every committed seek, engine failover, audio-route reload, and audio-track switch (which in current Exo code itself forces a seek, `PlayerRuntimeControllerTrackSelection.kt:74-77`). Anchor latency budget: mapping error ≤ ±40 ms at anchor points, ≤ ±80 ms steady state, measured on impulse-marker fixtures (see matrix M4). Replay of stale epochs must be structurally impossible: chunk acceptance requires `(generation, seekEpoch)` match with the session coordinator's current values.

**R2 — Buffering.** Bounded, explicitly sized ring between acquisition and provider, and between provider and playout: (a) acquisition ring ≥ 12 s and ≤ 30 s of PCM ahead of the provider cursor; (b) translated-audio playout buffer targeting ≥ 10 s / ≤ 45 s of playable audio at 1× after settling (headroom for the measured 1.5× expansion plus provider jitter); (c) hard byte ceiling with drop-oldest on the *translated* side only, never on the original-audio acquisition; (d) buffer starvation is a surfaced state ("Original fallback"), never silence-as-success; gap→original crossfade ≤ 300 ms and state visible ≤ 500 ms after detection. No unbounded queue may live on the playback thread; all queues are host-session owned and freed at release.

**R3 — Segmentation.** Provider input windows: 100–250 ms PCM frames (the Qwen receipt used 100 ms, `benchmarks ... .json:21`). Playout segments (Option B): 1–2 s AAC-in-fMP4 (or equivalent) on the source-time grid; segments are published atomically (never rewrite an advertised segment); live edge = last complete segment; bounded manifest history (≤ 10 sliding window entries + ≤ 3 back-fill); every segment records the exact `S_t` interval it covers. A segment that would cover a not-yet-translated region is emitted as an explicit gap object in the manifest (coverage map), not as silence and not as repeated audio.

**R4 — Correction.** Duration expansion is expected (measured 1.524× and 1.565×, `benchmarks ... .json:38,61`; audit §3 "no mapping from source media time to playable target samples exists"). Correction budget: cumulative tempo adjustment within ±8% per speech region and ≤ ±4% rolling average; insertion/removal of silence only in silence gaps ≥ 300 ms; hard resync (regenerate region, crossfaded ≤ 150 ms) when |error| > 250 ms or drift slope projects > 250 ms within the next 60 s. Phase error is estimated from marker pairs (fixture impulse markers vs provider chunk timestamps), never from packet arrival. All correction terms are logged per interval; user-visible base delay is separate (reuse the existing audio-delay model conceptually — but note `AudioDelayMediaSource` implements delay by rewriting *video* sample timestamps, `AudioDelayMediaSource.kt:96-104`, which a dub path must not naively inherit since audio is the master clock there).

**R5 — Seek generation.** Every committed seek increments `seekEpoch` and: cancels in-flight provider work for prior epochs, discards non-EOS-flushed partial chunks, re-covers `[seekTarget − preRoll, seekTarget + lookahead)` where preRoll ≤ 2 s (enough sentence context) and lookahead ≤ 10 s, and marks the manifest/coverage so the player falls back to original audio until target coverage is playable. Seek sources that must all route through the one coordinator: UI seek-by/preview/seek-to (`PlayerRuntimeControllerPlaybackEvents.kt:1183-1236`), audio-track switch nudge (`PlayerRuntimeControllerTrackSelection.kt:74-77`), error recovery re-init (`PlayerRuntimeControllerErrorRecovery.kt:62,287,295,381,430,481,489` all call `initializePlayer`), engine failover (`PlayerRuntimeControllerEngineFailover.kt`), resume-at-start (`NuvioMpvSurfaceView.kt:42-68` start option). Budget: return to generated audio after a 5/30/60-minute seek within a product-defined bound (proposed ≤ 15 s at p95), zero stale-epoch packets audible (verified by marker identity).

**R6 — Reconnect, failover, lifecycle.** Provider socket reconnect with capped exponential backoff (≤ 5 attempts, ≤ 30 s total) resuming from the acquisition ring's oldest uncovered `S_t`; resume must re-send only uncovered audio (billing gate below) and must not re-transcribe already-covered regions. Source reconnect reuses `LoadErrorHandlingPolicy`-style bounded retries on the acquisition client only — auxiliary failures never consume primary playback retry or failover budget. Engine failover must preserve session identity by stable generated-track key and re-attach on the target engine (MPV `audio-add`/Exo override) without regenerating already-covered regions. Release semantics mirror `PlayerRuntimeControllerLifecycle.kt:31-63`: every job cancelled, sockets closed, ring freed, token revoked, and late provider callbacks rejected on sight of a dead epoch — plus the one gap current lifecycle has: nothing today invalidates a loopback artifact mid-flight because no such artifact exists yet; the coordinator must make token revocation part of `releasePlayer`.

**R7 — Long-form measurement.** Per finalist provider: three 22-minute episodes and one 100-minute title; record p50/p95 first-playable and steady-state source-to-playback lag, marker sync error, drift per 20 min, gap/repeat/reconnect counts and loss, output/source duration ratio, correction magnitudes, CPU/PSS/FD stability, cost per completed playable minute, and invoice reconciliation within 10% for ≥ 95% of jobs. Duration ratio and correction bounds get their numeric acceptance only from the listening study (brief §"Source audio and remix quality boundary"); the transport gates (80 ms median / 150 ms p95 after settling; ≤ 1 s cumulative drift per 20 min; no video stall attributable to the auxiliary path > 500 ms) are pass/fail now. No timing number from vendor marketing or from the existing single-clip receipt may be quoted as a latency claim (audit §3, §4).

## Findings

Finding: F1 — Exo audio tap is single-selection, single-sink; it structurally cannot carry original audio while a generated track is selected, and the only existing processor chain deactivates for passthrough/offload formats.
Evidence: `PlayerRuntimeControllerInitialization.kt:2065-2096` builds one `DefaultAudioSink` wrapped in `PlaybackSpeedAwareAudioSink`; `:2098-2136` passes that one sink to every audio renderer (MediaCodec replacement `PlaybackSpeedAwareAudioRenderer` at `:2124-2133`, FFmpeg extension at `:2135`); `PlayerRuntimeControllerTrackSelection.kt:69-73` selects audio exclusively via `TrackSelectionOverride`; `PlaybackSpeedAwareAudioSink.kt:99-127` deliberately permits AC-3/DTS/TrueHD passthrough and offload whenever Bluetooth/non-1× speed has not forced PCM; `GainAudioProcessor.kt:33-38` returns `AudioProcessor.AudioFormat.NOT_SET` for any non-PCM encoding, so no PCM exists at the chain in those sessions.
Impact: Any Phase-B design that assumes "the current audio renderer also feeds the provider" loses the original-audio feed at the exact moment translated audio becomes the selected track, and has no PCM at all during bitstream passthrough sessions common on AV receivers — the primary TV use case. It would also risk the provider transcribing generated audio once selection flips.
Fix: Treat the decision doc's independent-acquisition requirement as hard: implement host-owned second demux/decode (Option A) or loopback proxy (Option B) in Milestone 5; forbid any provider input derived from the playback sink. Keep the sink tap idea only for the *subtitle* MVP with its explicitly documented PTS limitations.
Priority: P1
Confidence: high

Finding: F2 — The AudioProcessor seam has no presentation timestamps, so source-time anchors required by the acceptance gates cannot be derived from it even when PCM is flowing.
Evidence: `GainAudioProcessor.kt:40-56` implements `queueInput(ByteBuffer)` as a pure sample transform with no time parameters; Media3's `BaseAudioProcessor` contract exposes no PTS, discontinuity, or playback-head relationship; the decision doc itself records "a raw `AudioProcessor` callback has no authoritative PTS" (`decision.md`, "Player input and output seams differ").
Impact: Chunk timestamps invented at this seam would drift or jump at renderer reconfigurations (track switch, route change, PCM fallback latch in `PlaybackSpeedAwareAudioSink.setPlaybackParameters`, `:80-93`), violating the ≤ 80 ms/150 ms sync gates and contaminating seek epochs.
Fix: Source time must come from the acquisition path's demuxer PTS (container domain), correlated to player position only at defined anchor events; the player position source per engine is `player.currentPosition` (Exo) and `time-pos/full` with `paused-for-cache` invalidation (MPV, `NuvioMpvSurfaceView.kt:160-186`).
Priority: P1
Confidence: high

Finding: F3 — MPV wrapper exposes no decoded-audio observation and no `audio-add`/`audio-remove`/`audio-reload` adapter; the only external-track command is `sub-add`, and audio selection is exclusive `aid`.
Evidence: `NuvioMpvSurfaceView.kt:620-622` (`observeProperties()` empty — progress polled by controller), `:462-480` (`sub-add ... cached` only), `:420-429` (`setPropertyInt("aid", trackId)`), `:140-143` (`aid`/`sid` reset to `auto` on every new load); repository-wide search for `audio-add|audio-remove|audio-reload` outside docs/graphify-out/build returns nothing; mpv dependency is `io.github.abdallahmehiz:mpv-android-lib:0.1.12` (`app/build.gradle.kts:496`).
Impact: The brief's Milestone 2 (finalized-artifact attachment via MPV `audio-add`) has zero code and zero binary proof today; assuming libmpv command availability without a device probe risks building Phase A on an unverified seam, and live original-audio feed from MPV playback is impossible from this wrapper.
Fix: Before any UI work, run the M0/M2 binary probes in the matrix (real `audio-add` attach/select/seek/remove cycles on the bundled mpv); add the tested adapter with track-list observation; keep MPV live capture out of scope until a native seam exists (decision doc delivery sequence step 6).
Priority: P1
Confidence: high

Finding: F4 — MPV applies request headers as one global runtime property, so any loopback rendition (artifact server or proxy) attached with `audio-add`/`sub-add` inherits the primary origin's Authorization/cookies unless headers are explicitly cleared per request.
Evidence: `NuvioMpvSurfaceView.kt:624-639` — `applyHeaders` sets the single `http-header-fields` property before `loadfile` (`setMedia` calls `applyHeaders(headers)` at `:49` and `:109`), and there is no per-URL header override; `buildMediaRequestKey` (`:641-647`) includes headers, proving header state is media-scoped global state. Primary headers include Authorization for WebDAV/debrid-style sources (`PlayerPlaybackNetworking.kt:94-121` adds an Authorization-preserving interceptor; `PlayerRuntimeControllerStreams.kt:795-808` applies `proxyHeaders.request`).
Impact: A Phase-A/B loopback URL fetched by mpv would carry the primary stream's credentials to the loopback server — leaking debrid/auth token values into a local HTTP request (readable by any co-resident app that can reach the port, and potentially into mpv logs), violating the decision's invariant "Primary Authorization/Cookie/Host/userinfo/query credentials never reach provider, auxiliary host or loopback logs".
Fix: The adapter that adds generated tracks must (a) bind the loopback server to 127.0.0.1 only, (b) require an unguessable per-session token in the path, (c) clear/override `http-header-fields` for the loopback request (per-file `loadfile` options or property save/restore), and (d) assert in M2 that the loopback access log (test builds) contains no primary header values.
Priority: P1
Confidence: high

Finding: F5 — Loopback-port allocation is already contested in this app: TorrServer is hard-pinned to 8091 on 127.0.0.1 while `StreamBadgeConfigServer` defaults to wildcard NanoHTTPD on the same 8091; other config servers sit on 8080/8090, all wildcard-bound and untokenized.
Evidence: `TorrServerBinary.kt:28,40` (`const PORT = 8091`, `baseUrl = "http://127.0.0.1:$PORT"`, started with `--port 8091` at `:80`); `StreamBadgeConfigServer.kt:27-28` (`port: Int = 8091`, `NanoHTTPD(port)` wildcard bind, no auth in `serve()`); `AddonConfigServer.kt:20-21` (8080), `RepositoryConfigServer.kt:16-17` and `DebridFormatterConfigServer.kt:17-18` (8090), all NanoHTTPD.
Impact: A new artifact/proxy server that follows the fixed-port precedent will collide with TorrServer during torrent playback (the dub use case on torrents) or with a config server, failing attach exactly when both features are active; following the wildcard/untokenized precedent would expose artifacts to the LAN, against the decision's loopback-only tokenized invariant.
Fix: The `LocalMediaArtifactServer`/`DubSessionProxy` must bind loopback-only, take an OS-assigned ephemeral port (bind port 0, read back), carry a random 128-bit token per session, and register in one in-process port registry so collisions with TorrServer (dynamic or pinned) and config servers are detected at bind time.
Priority: P1
Confidence: high

Finding: F6 — Engine-failover and track-carryover logic re-applies language/track identity across Exo→MPV switches, but nothing exists to carry a generated-track generation, delay, or coverage across failover; the failover snapshot has audio/subtitle language identity only.
Evidence: `PlayerRuntimeControllerEngineFailover.kt:200-340` snapshots the selected audio track (language/name/id) and subtitles from `readTrackSnapshot()` and re-applies preferences on the target engine; `NuvioMpvSurfaceView.setMedia` resets `aid`/`sid` to `auto` per load (`:140-143`); there is no session coordinator, no generation counter, and no seek epoch anywhere in `app/src/main/java` (searched: `MediaTransformSessionCoordinator|DubPlayback|ExternalAudioDescriptor` → no matches).
Impact: On engine failover mid-dub (an expected recovery path in this app), the design as-is would either lose the generated track entirely or re-attach a stale artifact with wrong position/delay — the exact "stale descriptor" failure the brief forbids ("Episode and source switches never reuse a stale descriptor or delay blindly").
Fix: Introduce the session coordinator as the single epoch authority (R5/R6) and require failover to restore by stable generated key + coverage map, not by re-adding whatever file remains; failover must count as a seek epoch with re-anchoring.

Finding: F7 — Seek behavior differs per engine and per path with no unified hook: Exo seeks use NEXT/PREVIOUS/CLOSEST_SYNC variants and an in-buffer fast path, MPV seeks are absolute `time-pos` writes; audio-track switches and error recovery silently generate additional seeks.
Evidence: `PlayerRuntimeControllerPlaybackEvents.kt:1183-1236` (direction-dependent `SeekParameters`, preview-seek commit with CLOSEST_SYNC), `PlayerRuntimeControllerMpv.kt:521-559` (`setSeekParameters` + `seekTo` on Exo; `view.seekToMs` on MPV with delay re-application), `NuvioMpvSurfaceView.kt:174-178` (`setPropertyDouble("time-pos", seconds)`), `PlayerRuntimeControllerTrackSelection.kt:74-77` (audio switch nudges `seekTo(pos-1)`), `PlayerRuntimeControllerErrorRecovery.kt:62,287,295,381,430,481,489` (multiple `initializePlayer` restarts that re-seek to saved position).
Impact: A dub implementation that hooks only the visible UI seek will miss track-switch seeks, error-recovery re-inits, and failover re-positions; each missed path yields stale-epoch packets, double-translated regions (cost), or coverage gaps heard as silence.
Fix: Route every listed path through one seek-generation entry point in the session coordinator (increment epoch, cancel, re-cover, fallback state) — enumerated exhaustively in R5; add an instrumentation test that fires each path and asserts a single epoch increment each.

Confidence: high

Finding: F8 — Torrent input already provides a localhost HTTP clear source (TorrServer), which is the cheapest acquisition substrate for Option A/B on torrents, but its lifecycle is tied to playback flush and its stream identity is a magnet-encoded query string with no explicit range/EOF contract in the app.
Evidence: `PlayerRuntimeControllerTorrent.kt:18-44` (start returns local URL), `:49-62` (stop cancels jobs and drops torrent), `TorrentService.kt:49-105` (add → `getStreamUrl` → `dropTorrent`; `stopStream` in `releasePlayer(flushPlaybackState=true)` via `PlayerRuntimeControllerLifecycle.kt:15-18`), `TorrServerApi.kt:145-148` (`/stream?link=<urlencoded magnet>&index=<idx>&play`), and `PlayerRuntimeControllerTorrent.kt:182-184` sets `currentHeaders = emptyMap()` for the local URL.
Impact: A dub session on a torrent stream will lose its acquisition source whenever playback state flushes or the app drops the torrent for recovery/failover; conversely, keeping TorrServer alive for dub-only work extends background torrenting beyond playback lifetime (against the "no background paid work after leaving playback" non-goal when combined with billing).
Fix: The acquisition layer needs an explicit reference-counted lease on the torrent stream independent of `stopTorrentStream()`, plus a documented range-support/EOF probe of TorrServer's `/stream` endpoint (M6 in the matrix) before relying on it for arbitrary seek-window regeneration.
Priority: P2
Confidence: medium

Finding: F9 — Clear-VOD boundary is currently implicit (no DRM configuration is ever set), so the "known encrypted input → zero provider calls" gate has no detection point; the media path builds `MediaItem` without `DrmConfiguration` and treats HLS/DASH purely by MIME.
Evidence: `PlayerMediaSourceFactory.kt:84-113` and `:197-205` (MediaItem built with URI/mimeType/subtitle configurations only; `HlsMediaSource`/`DashMediaSource` chosen by inferred MIME); repository search for `DrmConfiguration|Widevine|DrmInitData` in player sources returns no matches; stream identity is `url + infoHash + clientResolve` (`domain/model/Stream.kt:10-153`) with no encryption fields.
Impact: An encrypted HLS/DASH or DRM MP4 source could reach a dub session that assumes "clear" because nothing downstream failed; the provider would then receive encrypted/watermarked audio bytes (quality garbage) and the decision's invariant 8 plus the brief's security gate 6 would be violated silently.
Fix: Add a fixture-driven refusal test: presence of `DrmInitData` in the acquisition demux (or HLS master with encrypted KEYFORMAT, or `MediaItem.localConfiguration.drmConfiguration`) must fail the session closed before any provider call; cover in matrix cell M7.
Priority: P2
Confidence: medium

Finding: F10 — Existing measured evidence cannot support any sync/latency/cost gate: the single Qwen receipt is a confounded two-run smoke test with 1.52–1.57× duration expansion, no source timestamps, no retained raw events, and no invoice record; the audit already rates it HIGH-severity evidence.
Evidence: `benchmarks/2026-08-29-qwen-live-translate.json:24-67` (two success probes changing voice, clone and source-ASR together; `output_audio_seconds` 14.96/15.36 vs 9.814 source; `first_audio_after_session_update_seconds` 1.3045/3.4576), `:96-101` (derived findings themselves), `:102-107` (evidence limits: one synthetic clip, no long-form/drift/invoice); `audits/model-research-audit.md` §3 ("confounded", "no mapping from source media time to playable target samples exists", receipt "a useful self-reported smoke-test summary only") and §4 (incomparable latency ranks).
Impact: Sizing decisions made from these numbers (buffer depths, first-playable targets, per-minute cost) would be wrong by unknown margins; in particular, any design that assumes near-1× output duration will accumulate >0.5 s of error per minute of dialogue at the observed expansion ratio, overwhelming any correction budget.
Fix: Gate Phase B entry on the rebuilt harness (retained raw events, source SHA-256, factorial clone ablation, invoice reconciliation per audit follow-ups 1/3/9/11) and on the long-form corpus of R7; treat all current numbers as hypotheses to falsify in matrix cells M8–M11.
Priority: P2
Confidence: high

Finding: F11 — Playback-position semantics are engine- and state-dependent (Exo smoothed position vs MPV playback time that freezes under cache stall), and MPV progress polling is the only progress source, so a naive single "current time" call is not a valid sync anchor during stalls.
Evidence: `PlayerRuntimeControllerMpv.kt:486-492` (`currentPlaybackPositionMs` returns `mpvView?.currentPositionMs()` or `player.currentPosition`), `NuvioMpvSurfaceView.kt:180-186` (`time-pos/full` read), `:160-172` (`isPausedForCacheNow`/`isCoreIdleNow` expose the stall states), `:620-622` (no property observation; poller-based progress).
Impact: Anchoring provider playback to a stalled or smoothed clock during rebuffer produces systematic lead/lag that correction then "chases"; on torrents (frequent `paused-for-cache`) this would look like provider drift when it is clock error.
Fix: Define the anchor as in R1: MPV time valid only when not `paused-for-cache`/`core-idle`; Exo anchor taken at defined listener events; correction must hold (not accumulate) while the position source is invalid.
Priority: P2
Confidence: medium

Finding: F12 — The existing audio-delay mechanism rewrites video sample timestamps (audio-as-master-clock reasoning), so reusing it unchanged for a translated-voice path would interact with segment timestamps and correction in non-obvious ways.
Evidence: `AudioDelayMediaSource.kt:96-104` — comment "Audio is the master clock in normal playback, so shifting audio timestamps tends to pull video along with it. Shift video timestamps in the opposite direction", implemented by subtracting delay in `AudioDelaySampleStream.readData` (`:152-163`) for TRACK_TYPE_VIDEO and compensating in `skipData`.
Impact: A dub rendition whose PTS grid was also shifted by this wrapper (if attached through the same MediaSource path) would double-apply delay semantics; on MPV, `audio-delay` (`NuvioMpvSurfaceView.kt:253-265`) applies to *all* audio including the generated track, conflating user base delay with runtime correction.
Fix: Keep user base delay and runtime correction as separate terms exactly as the brief specifies (Milestone 6); the proxy's segment grid must be source-time-native, with delay applied only at the final playout boundary, and MPV `audio-delay` must be accounted as one named term in the correction equation.
Priority: P2
Confidence: medium
